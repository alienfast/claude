# Issue Spec Standard

A **certified spec** is an issue description that states the problem, the desired outcome, and testable success criteria — reviewed by a human (or produced by a trusted pipeline) and marked with the `specified` label. Certification is what makes an issue safe for unattended pickup: `/auto` builds only certified issues.

Specs describe the **WHAT, never the HOW**. Implementation planning — technical approach, file lists, step-by-step design — happens in `/start` Step 6 (plan mode) at execution time, against the codebase as it exists then. Verification commands belong to project quality gates (`pnpm check`), not the ticket.

**When the work IS site enumeration** — a normalization sweep, an encoding pass, "these N call sites lack the guard" — the ban on file lists still holds for *planning*, but the census is the requirement and has to live somewhere. This is a gap the ban alone leaves open, and with nowhere sanctioned to put the census an author writes bare line numbers into the criteria. Write it so it degrades honestly instead of lying:

- Describe each site by **greppable code shape** (`inv.Status !== 'VOIDED'`), never by line number alone. A shape survives every edit that does not change the defect; a line number is wrong after the next commit.
- **Anchor the census to a commit** — "as of `<sha>`, six sites" — and say in the body that line numbers are a convenience, not a specification. A reader can then tell a stale count from a wrong one.
- Make the count **re-derivable**: state the grep that produces it, so pickup re-runs the census rather than trusting it.

In a fleet this decays fast, because parallel sessions land adjacent work continuously and nothing detects the decay. Measured 2026-08-20: an issue certified naming six raw `Status` sites at specific lines had two left by grooming — four fixed in the interim, two cited lines gone — and a sibling certified hours earlier the same session went stale within hours when another session merged into the file it names.

## The `specified` label

- **Semantics:** this issue's description is a certified spec — "an unattended agent may pick this up and ship it."
- **What it gates:** `/next <label>` filters candidates to a label; `/auto` dispatches `Skill(skill: "next", args: "specified")`, so only certified issues ship autonomously. Bare `/next` stays unfiltered — humans may deliberately work uncertified issues.
- **Who applies it:** `/prd` (single-issue runs on create; batches after collision edges wire), `/spec` (after research + interview + explicit signoff), `/reflect`'s filing script (its proposal bodies already carry problem/outcome/criteria), `/quality-review`'s deferred-item filing — only for severity-carrying items (pre-existing Critical/High/Medium findings, routed by its Step 5 fix-loop lane split, by its Step 5 auto-mode ceiling resolution (Medium survivors only), or by its Step 6 sub-step 5 re-review) that additionally clear the quality bar below; severity decides whether it files, the bar decides whether it certifies, and an item below the bar files uncertified for `/spec`. Its Nice-to-Have lane never files at all — or a human in Linear when they judge a spec complete.
- **One workspace-level issue label.** `linear-cli labels create "specified" -t issue` creates it workspace-wide (the CLI cannot create team-scoped labels — a feature here: one label attaches across all teams). Never create team-scoped `specified` duplicates — name-based label operations become ambiguous.

## Applying the label — read-merge-set

`linear-cli issues update -l` **replaces the entire label set** (there is no add/remove subcommand). Always add through the helper, never a bare `-l`:

```bash
~/.claude/scripts/linear-add-label.sh PL-13 specified
```

It reads current labels, merges, sets, and verifies the attach; idempotent when the label is already present; exit 2 with a create-label pointer when the label is missing or unattachable. Direct `-l` is acceptable only on a just-created issue, whose label set is empty by construction.

## Certification includes collision edges

`specified` is the pickability gate: the moment it attaches, `/auto` may select the issue in any session, so sequencing between issues must already be mechanical by then. Every producer attaching the label owes a collision check at attach time, and the check has two outputs. A **`blocks` edge** (`linear-cli relations add <BLOCKER> <BLOCKED> -r blocks`) means exactly one of three things and nothing else (keeper ruling 2026-09-11): a **prerequisite** — the blocked issue needs the blocker's code, schema, API, migration, or decision to be implementable or testable; a **same-method collision** — both issues will edit the same function, predicate, mutation resolver, or component body, where merging is judgment rather than mechanics; or a **deliberate increment** — a human wants the order (surgical fixes before the sweep that enumerates them, step N of a migration). `next-candidates.sh` hides blocked issues, so a `blocks` edge is the one control that prevents concurrent pickup — and the one that idles a lane until the blocker ships. A **`related` edge** (`-r related`) records every other overlap: the same file in different regions, a shared spec, locale, or config file, a shared mechanism or helper. It has teeth of its own — `next-candidates.sh` soft-de-ranks a candidate whose `related` partner is in flight, so a fleet prefers non-overlapping work while any exists and takes overlapping work only when nothing else remains — and the merge is verified rather than scheduled around: `/finish` re-runs the project check on the merged tree whenever the source branch advanced under the issue (`finish-merge.sh` exit 5). Same file alone was a `blocks` case until 2026-09-11; measured on BF that day, 57 of 222 certified issues sat behind a workable blocker and nearly every cross-parent edge was a file-family serialization, against 34 merge conflicts across 669 shipped issues, every one resolved in-session — the rule was scheduling around a cost that turned out small and self-healing while hiding a quarter of the pool. No overlap takes nothing. Description prose is never a scheduling control — `next-candidates.sh` reads relations and labels, not text. `/auto-prep`'s batch linking remains the pool-level sweep (collisions between issues certified far apart, and edges gone stale after ships); attach-time linking closes the window between certification and the next prep run.

Wiring a `blocks` edge is a guard, not a reflex: wire one only when the blocked side is (or is about to become) fleet-pickable (`specified`) and the blocker will actually ship unattended — certified, not `needs decision`, not `solo` — mirroring `/auto-prep`'s "never chain through a Step 2-flagged issue" doctrine, since blocker resolution reads the blocker's *state*, never its labels, and `next-candidates.sh` filters blocked issues out before ranking, so anything wired behind a blocker that never ships unattended is stranded invisibly. When the would-be blocker is uncertified, `needs decision`, or `solo`, record the overlap as `related` plus a comment naming the shared file instead — **with one carve-out for `solo`**: unlike the other flags a `solo` issue does ship, just outside the fleet window, so it may be wired as a blocker when it is a chain HEAD you will run in the pre-fleet quiet window (`/auto-prep` § Step 3). A `solo` issue anywhere else in a chain still takes `related`, or its dependents stay blocked for the whole run. Direction: the blocker is whichever issue should land first — semantic/work order when discernible (mechanism before consumers, a surgical fix before the sweep that enumerates its area); failing that, preserve any existing reachability in the group, so a pre-wired chain head stays the head rather than being buried by a fresh sort; failing that, the earlier/already-open issue blocks the newer one. A producer that structurally attaches the label before wiring edges (a single-issue grooming run certifies before its collision check runs; a `/reflect` filing's issue ID exists only after the filing script returns) closes the resulting window by wiring immediately after attach — the window is seconds long and accepted. A producer without code context applies the check at the finest granularity it has — `/prd` works from component and feature decomposition, never file lists — and that coarser judgment satisfies the obligation.

**When the overlap partner already sits in a chain, wire into the chain — a pairwise-correct edge can still leave a live collision.** The direction rule above settles only the *pair*, and a prepped pool routinely carries a multi-issue chain over one hot method or mechanism (`/auto-prep` § Step 3 wires them). Attaching the new issue to a non-tail member forks that chain rather than extending it: when that member ships it releases both its original successor and the new issue, and the two then run concurrently against the very method the chain exists to serialize. The attach point is systematically the wrong one — a dedup search returns whichever sibling it matched, and `/quality-review`'s parent→child edge points at the issue being shipped *right now*, an edge that skill designs to self-clear the moment `/finish` moves the parent to `Ready For Release`. So read the hit's own relations before wiring (`linear-cli relations list <ID>`, reading **both** `.relations[]` and `.inverseRelations[]` — linear skill gotchas #13 and #22): a hit that already blocks or is blocked is a chain, not a pair. Attach at the **tail** — the last member that will ship unattended, since the flagged-blocker guard above still bars wiring behind a `needs decision`, uncertified, or non-head `solo` tail — and insert mid-chain only when semantic order demands it, wiring **both** edges, predecessor→new and new→successor; a lone incoming edge *is* the fork. One extra read, and a chain case costs two edges rather than one. Then confirm every pair in the group is mutually reachable, as `/auto-prep` § Step 3 already requires for its pool-level sweep: adjacent-pairs-only wiring plus a pre-existing chain makes a group *look* serialized while a pair sits unordered, and nothing downstream reports it. Measured across two consecutive fleets, six filings, five of five carrying only a parent edge: on 2026-08-22 a mid-fleet filing overlapping an eight-issue chain over two reviewer route files carried only an edge to the chain's second member — the issue then in flight, and its parent — which released it hours later alongside the chain's still-unshipped remainder, both editing both files; the miss surfaced only at `/fleet-retro`'s filing audit a whole run later. On 2026-08-23 the parent edge was measured self-clearing **within the same fleet**, so it provides zero collision protection on the timescale that matters, and one filing that *did* search and *did* return a chain member still missed the tail it collided with — the failure is the choice among several valid-looking hits, not an absent search.

## The `needs decision` label

- **Semantics:** a human must step in before unattended pickup — the issue hit something no agent may resolve: a product/design decision with no testable success criteria, an unstated scope or mapping a criterion silently depends on, or an explicit do-not-ship-unattended note. (Work that is *itself* human-performed takes [`human`](#the-human-label) instead — that gate is permanent; this one clears when the decision lands.) The issue **keeps `specified`** — the spec is gated, not wrong; de-certifying would discard grooming work and hide *why* the issue is parked.
- **Filing before the decision exists:** an issue whose requirements cannot yet prescribe behavior — its criteria would read "decide X", which the quality bar forbids certifying — files **without** `specified`, carrying `needs decision` alone and saying so in the body. The keeps-`specified` rule above is for issues certified *before* hitting the gate; a decision-shaped filing earns certification only through re-grooming once the decision lands.
- **What it gates:** `next-candidates.sh` hides `needs decision` issues from every ranking — `/auto` never picks them, `/next` never suggests them — unless invoked with `--label 'needs decision'`, which lists exactly those (how `/spec` pick mode surfaces them). `/start` refuses to claim one in auto mode and warn-asks interactively.
- **Who applies it:** `/auto` on a decision-shaped durable decline or mid-flight stop (which also parks the issue back to `Planned`, unassigned — never `stalled`, which is reserved for pipeline failures; a stop whose gate is a human-performed *step* routes to [`human`](#the-human-label) instead), `/auto-prep`'s certification audit, and any skill that discovers a human-decision gate on an issue. Always paired with a comment naming the specific decision or access needed — the label flags, the comment explains. When the parking strands verified committed work (a preserved worktree whose branch carries green-verified commits), the comment also pre-stages the keeper's call: state the split-vs-wait option with the drift cost, so the decision is a one-question interview rather than a re-derivation — BF-858's second parking comment is the model.
- **Who clears it:** a human, once the decision is recorded on the issue — directly (`~/.claude/scripts/linear-remove-label.sh <ID> 'needs decision'`), via `/spec <ID>` (re-certification clears it), or by proceeding through `/start`'s interactive warn-ask (proceeding is the decision).
- **One workspace-level issue label**, same as `specified`: `linear-cli labels create "needs decision" -t issue`. `linear-add-label.sh` exit 2 gives this pointer when the label doesn't exist yet.

## The `human` label

- **Semantics:** the work itself is human-performed — customer outreach, vendor contact, production data remediation, sign-offs, briefings, or a roll-up a person owns. Unlike `needs decision` (agent work parked until a human decides), no pending input ever hands it back to an agent: no mode of any skill can ship it. The issue **keeps `specified`** when its spec meets the bar — certification records spec quality; this label records the executor.
- **What it gates:** `next-candidates.sh` hides `human` issues from every ranking unless invoked with `--label human`, which lists exactly those — the team's own to-do view. Unlike `solo` there is **no targeted-mode carve-out**: `/auto <ID>` refuses a `human`-labeled target, and `/start` warns interactively (proceeding assists a human owner; the label stays) and skips in auto mode — running it is not a remedy an agent can provide.
- **Distinguish from `needs decision`:** that one clears — decision recorded, label removed, an agent ships it. This one lives as long as the issue does; it clears only by re-scoping through `/spec`, typically splitting the agent-shippable slice into its own issue while the human acts keep the label. The routing test is *what the human must do*, not how much agent work surrounds it: a partially-implemented issue whose **remaining** gate-step is human-performed (console/credential configuration, a vendor contact) takes this label too — recording an answer on the issue would hand nothing back, and the keeper's `needs decision` sweep (`/spec`) would find no question to answer. When agent work remains after the human acts, the hand-back is the same re-scope — or the human clears the label after acting, which is that decision made directly.
- **Who applies it:** `/prd` at certification for human-executed sub-issues, `/auto-prep`'s Step 2 audit for the same class, `/auto` on a capability-shaped durable decline or mid-flight park, a boundary-collision route-out filing whose gate is a human-performed act (§ Out of Scope bounds the deliverable, never the evidence), or a human. Pair it with an assignee or a comment naming who owns the work when known.
- **One workspace-level issue label**, like the others: `linear-cli labels create "human" -t issue`.

## The `solo` label

- **Semantics:** shippable unattended, but not *concurrently*. A `/start wt` worktree isolates the working tree, and nothing that makes these issues dangerous lives there — the merge point every session shares and the `pnpm check` command every concurrent session hard-gates on. Typical members: repo-wide sweeps, and edits to the root `package.json` or the shared check suite. (Schema/codegen regeneration is NOT solo — keeper ruling 2026-08-15: `schema_gen` is a routine task, and a description-only regen manifests as comments with zero code implications.) The issue **keeps `specified`** — it is certified, just not parallelizable.
- **What it gates:** exactly one thing — the automatic pick. `next-candidates.sh` hides `solo` issues from every ranking (`/auto` never picks one, `/next` never suggests one) unless invoked with `--label solo`, which lists exactly those. It is deliberately **not** a claim-time refusal: `/auto <ID>` and `/full <ID>` ship a solo issue normally, since targeted mode gates on `specified` alone and running it *is* the remedy. Never add a refusal on this label — that would strand automatable work.
- **Distinguish from `needs decision`:** that one means a human must *decide* something and the issue must not ship until they do. This one means no human is needed at all, only an empty fleet.
- **Who applies it:** `/auto-prep`'s certification audit (Step 2's solo disposition), or a human who knows an issue will collide with everything else in flight.
- **Who clears it:** whoever ships it — a scheduling constraint on an open issue dies with the issue. Clear it early (`~/.claude/scripts/linear-remove-label.sh <ID> solo`) only if the blast radius proves narrower than the audit judged.
- **How to run one:** while no fleet is active, first or last, never mid-fleet. `~/.claude/scripts/next-candidates.sh --label solo` lists the pool; `/auto <ID>` ships one unattended; `/fleet-sequence <ID> <ID>...` ships several strictly in order as a PR stack, each in its own background session and forked from the previous one's branch.
- **One workspace-level issue label**, same as `specified`: `linear-cli labels create "solo" -t issue`.

## The `simple` label

- **Semantics:** the change is **risk-low** — its blast radius is one a verifier-tier review can bound without discovery. All of these hold: the remedy touches no authorization/policy predicate or gate, no tenant- or viewer-scoping check, no money-movement / ledger / KYC-state semantics, no lock or transaction boundary, no public contract other callers depend on (an additive nullable field, a description string, a type annotation, or an internal helper move is fine; removing or reshaping a schema field or a mutation's error contract is not), and no data migration beyond an additive index or constraint on a column whose invariant already holds — and it needs no **open decision**: a prescribed default the run simply records ("order by id desc") is fine; a choice between structurally different remedies, a "measure first" precondition that determines the remedy, or new infrastructure (a harness, a scanning guard, a scheduled job) is not. **Effort is not the gate.** Spec-only, story-only, doc-only, locale-only, and many-site sweeps of trivially safe edits qualify regardless of file count; effort enters only as `/quality-review`'s reviewability ceiling (~8 files / ~300 lines of non-generated diff), above which the run escalates. Never on a `security`, `human`, `needs decision`, or `epic` issue; coexists with `bug` and `solo` (fleet-hostility is not complexity). The issue **keeps `specified`** — this label describes the review the work needs, not whether it is certified.
- **Distinguish from `solo`:** that one is about *when* an issue may run (never concurrently with a fleet); this one is about *how much review* its change needs. They are orthogonal and routinely coexist.
- **What it gates:** exactly one thing — the review tier. `/start` reads it from the digest and passes `simple` to `/quality-review`, which runs its simple tier: one `quality-verifier` scoped review in place of `quality-reviewer` discovery, at most two review cycles, and fail-closed escalation to the full tier on any of four guards — the diff exceeds the ceiling, a forbidden co-label is present, the verifier answers `ESCALATE:`, or a Critical/High finding lands on the change at any cycle (any fix regression at cycle 2). The residual the guards do not cover — a mislabel the verifier's risk read misses that surfaces no Critical/High — ships with verifier-only review; the semantics above, the ceiling, and `/auto-prep`'s re-audit bound it, and it is the tier's accepted trade. It never affects pickability, ranking, collision edges, or `/finish`'s gates — `next-candidates.sh` ignores it.
- **Interactive override:** the `simple` token on `/start`, `/full`, or `/quality-review` selects the tier without the label; the label is how the fleet, whose only input is Linear, gets the same behavior. The guards apply to both — a typed token is a request, never an exemption.
- **Who applies it:** a human; `/spec` at certification when the groomed spec meets the semantics above; `/prd` on qualifying sub-issues; `/quality-review`'s deferred filing, under the stricter mechanical-lane bound an unattended producer must use; and `/auto-prep` Step 2, the backstop — in **both directions**, since a body's risk reads differently as the code around it evolves.
- **Who clears it:** the run that escalates (`~/.claude/scripts/linear-remove-label.sh <ID> simple` plus a comment naming the trigger, so the next pickup does not repeat the mismatch); `/auto-prep` when the body no longer qualifies; otherwise it dies with the issue.
- **One workspace-level issue label**, same as `specified`: `linear-cli labels create "simple" -t issue`.

## The `keeper` label

- **Semantics:** the work edits the shared user-level `~/.claude` repo (its `CLAUDE.md`, `rules/`, `standards/`, `skills/`, `scripts/`, `hooks/`). That repo is not the project repo any session is checked out in, so no amount of certification makes it shippable by `/auto` — a certified `~/.claude` issue produces a zero-commit false ship. These issues are filed **uncertified on purpose**: `keeper` attaches *instead of* `specified`, never alongside it.
- **What it gates:** two things. It hides the issue from the ranking on every machine whose `git -C ~/.claude config reflect.keeper` is not `true`, so teammates never see work only one machine can land; and on the keeper's own machine it promotes the issue to the top tier for interactive pickup. Because it never carries `specified`, `/auto`'s `--label specified` query excludes it regardless of tier.
- **Distinguish from `solo`:** `solo` is certified work waiting for an empty fleet. This is uncertified work waiting for a *specific human on a specific machine* — no fleet state makes it pickable.
- **Who applies it:** `~/.claude/scripts/linear-file-improvement.sh --keeper`, which `/reflect` uses for any batch whose targets include the user-level repo; or `/auto-prep`'s label repair.
- **Who clears it:** `/keeper`, when it adjudicates and ships the batch.
- **Never wire a `blocks` edge between two keeper issues.** Neither side is fleet-pickable, so there is nothing to serialize, and `next-candidates.sh` drops blocked issues *before* the keeper promotion — the edge would hide the batch from the keeper's own `/next` instead of protecting anything. Use `related`.
- **One workspace-level issue label**: `linear-cli labels create "keeper" -t issue`.

## Canonical spec template

```markdown
## Problem
<1-3 sentences: what is wrong or missing today, who is affected, why it matters now>

## Desired Outcome
<observable behavior/result after the work — user- or system-visible, never implementation>

## Requirements

### Must Have
- [ ] <core requirement>

### Nice to Have
- [ ] <optional enhancement>

## Success Criteria
- [ ] <specific, testable, implementation-agnostic criterion>

## Boundaries

### In Scope
- <what this ticket covers>

### Out of Scope
- <deliverable exclusions — work that belongs to separate tickets; § Out of Scope bounds the deliverable, never the evidence>

## Original request
> <verbatim original human text — only when regrooming an existing issue>
```

The checkboxes are load-bearing: `/start` Step 6 treats description checkboxes as requirements, and `/finish` checks them off on completion. Keep every requirement and success criterion a checkbox. (`### Nice to Have` boxes are the one exception — they carry the opportunity semantics below, are planned around only when trivially in-path, and gate nothing.)

**`### Nice to Have` means target of opportunity — not a requirement, and never a deferral.** Implement one only when it falls out easily from work already in hand; skipping is the normal outcome, needs no more than a one-line note at completion, and creates no obligation — no follow-up filing, no plan-comment promise, no unchecked-box guilt (`/finish` never gates on the tier). The tier's real value is at grooming: it is a brainstorm surface for other angles, and its only promotion path is a **human** moving a line into `### Must Have` (usually via `/spec`'s promotion pass). The machine never moves it anywhere — filing a skipped Nice to Have is feature creep, converting an optional brainstorm line into tracked work nobody prioritized (BF-1182, canceled: a skipped notify-others line filed `human` behind a vendor dependency on the precedent of BF-1123 — which gates a **Must Have**; the analogy fails on the tier). The same opportunity semantics govern `/quality-review`'s reviewer-finding Nice-to-Have lane: fix it if easy, otherwise record and drop — that lane never files.

## Quality bar — certify only if ALL hold

- [ ] Problem names who is affected and why it matters now
- [ ] Desired outcome is observable — verifiable without reading code
- [ ] Every success criterion is testable and implementation-agnostic
- [ ] Boundaries name at least one explicit exclusion — satisfiable by a deliverable exclusion; a mechanism-exclusion carries `(decided: <who/why>)` (§ Out of Scope bounds the deliverable, never the evidence)
- [ ] Sized for one focused session (<150k tokens of context); epic-sized work is broken into sub-issues — each certified individually — via `~/.claude/scripts/linear-create-child.sh`
- [ ] No implementation planning: no technical approach, no file lists, no verification-command blocks — unless the work *is* site enumeration, in which case the census follows the greppable-shape / commit-anchored / re-derivable form above. A `(decided:)`-marked mechanism-exclusion in Boundaries is the one sanctioned negative form (§ Out of Scope bounds the deliverable, never the evidence)
- [ ] No success criterion asks for a decision ("decide X", "determine whether Y" as an open question) — open product/design questions are resolved *before* certification, and the criterion prescribes the chosen behavior. An **empirical determination is not a decision**: a criterion may direct a measurement when it prescribes the response to each outcome ("measure whether the chain is reachable; if it is, bind the argument and assert the downstream predicate; if not, record why at the site") — the forbidden shape is the question left open, not the experiment (BF-673 shipped unattended on exactly such a criterion)
- [ ] No success criterion embeds a literal pattern (regex, glob, SQL predicate, field index) as its pass condition — state the property the data must have and let execution derive the check
- [ ] Original human text preserved under `## Original request` when regrooming

## A decision belongs in the description, never in a comment

A criterion reading "decide X" is not unattended-shippable. `/start` Step 6 takes "the issue description, checkboxes, and parent context as requirements", so the run re-derives the same open question and stops — and that decline is per-session (`/auto`'s skip lists live in `tmp/auto-state-<runKey>.json`, and `next-candidates.sh` reads no comments at all), so a fresh session ranks the issue first again and stops the same way.

Answering it in a comment does not fix this. The digest `/start` reads shows anchored comments in full but truncates standalone comments to the first 140 characters of their first line (`/start` Step 1 fetches the digest; the lossiness is documented at Step 6 — Step 4 is the one step the `/auto` path skips), and even a fully-read comment leaves the checkbox still saying "decide X". A comment recording only that a conversation happened — `Confirmed with <name>.` — is worse than none, because it looks like an answer.

When the decision lands, re-groom through `/spec <ISSUE-ID>`: write the answer into the description, quoting whoever decided and keeping any constraint they attached, and rewrite the criterion to prescribe the chosen behavior. Then leave a comment pointing at the description so an earlier `/auto` skip reads as resolved. This is the interactive, pre-run edit; an in-flight implementation run never rewrites the description.

## An either/or Desired Outcome is ordered — a fallback arm, not a menu

A Desired Outcome of the form "X cannot happen, or if it can, the failure is Y" names a preference and a fallback, in that order. It licenses shipping Y only when X is unreachable or out of proportion to the issue — it never makes the arms equal choices. When the implementing session's own investigation proves the stronger arm reachable — the evidence already in hand with no new investigation needed, the change within the files the issue's work already touches, and no product/design decision pending — delivering the stronger arm is **in-mandate**: "beyond this issue's mandate" cannot describe the issue's own first-choice outcome. Deferring it in that position files away the session's loaded evidence and re-prices cheap hot work at a full cold session (BF-673 measured the single-lock-scope change that closes its residual deadlock outright, shipped the retry arm, and filed the stronger arm as BF-1175 — whose success criteria cite measurements only the finished session could reproduce). When the stronger arm genuinely fails one of those gates — new investigation needed, a contract outside the issue's file scope, a pending human decision — the fallback plus a recorded reason satisfies the outcome, and any follow-up routes through `/quality-review`'s deferred-item bar rather than filing automatically.

**Distinguish the fallback form from a genuine fork.** The ordered reading applies when Y is a degraded handling of the very failure X prevents — "cannot deadlock, or the failure is retried/clean". A Desired Outcome offering two *complete end-states* — "either the twins align, or the divergence is documented as intentional with the reason" — is a fork, not a fallback: the arms are co-equal and the choice turns on judgment or a product call. A fork is resolved on its merits, never by reflex toward the busier arm (BF-1044's `resend?` criterion offered a grant or a recorded denial; the session correctly chose the denial, because the grant was far wider than the need). A fork whose choice is a product call the session may not make routes to `needs decision`, per this standard.

## Out of Scope bounds the deliverable, never the evidence

A spec's authority is asymmetric. Problem, Desired Outcome, and Success Criteria are a **mandate** — what the application should observably do — and only a human extends a mandate. A Boundaries exclusion makes one of two claims: a **deliverable exclusion** decomposes work ("Y is a separate ticket"), while a **mechanism-exclusion** ("the fix is not in X", "don't touch X's sizing") is implementation planning in the negative — a filing-time claim about where the cause is *not*, carrying the same stale-assumption risk that bans the positive form (WHAT-never-HOW, top of this standard). That distinction governs *writing* (the discipline below) and carries **no routing weight** — BF-1507's own exclusion reads plausibly as either kind, so a route keyed on the classification would be decided by whatever the session already wanted. What routes is the **marking**: `(decided: <who/why>)` records a human's call and is never crossed by an agent; anything else — `(assumed)`, or unmarked text, which is how every spec certified before this convention reads — is a **hypothesis**, falsifiable by the implementing session's own evidence under the gates below. The retroactivity is deliberate, not an oversight: the existing backlog's exclusions were all written pre-diagnosis, and the gates are the protection. Two one-way valves govern every collision: evidence can kill a hypothesis, never extend the mandate; the mandate can bound the diff, never suppress the evidence — whichever route below fires, the measurement surfaces (the plan comment, a checkpoint comment when the evidence arrives mid-implementation, and the completion comment). Silently honoring a boundary the evidence has falsified is not one of the routes — `(decided:)` exclusions included: there the crossing is refused, but the evidence still surfaces and routes.

**No exclusion bounds investigation.** Reading, measuring, and diagnosing inside excluded territory is always in-scope; the diff is what an exclusion bounds. And **a conditional exclusion must be measured, not presumed dormant**: "worth its own issue if it recurs" makes recurrence a question the session owes an answer to.

**When investigation proves the root cause of the issue's own Problem sits inside an exclusion — either kind — route as follows.** A `(decided:)` exclusion is never crossed: skip the gates and take the route-out branch below, addressing the evidence to whoever decided. Any other exclusion is a hypothesis, and three gates decide (adapted from the either/or section's in-mandate logic — deliberately wider on geography; see the material-difference rule below):

1. **In-repo** — the change lands in files this repo governs. Machine state, vendor consoles, and other repos always fail this gate.
2. **Evidence-in-hand** — the cause is measured, not inferred, and the evidence is already strong enough to survive review with no new investigation.
3. **No behavior left to decide — pinned vs. picked.** The test is whether an existing authority pins the behavior the fix produces — this spec's Outcome/Criteria, an existing test, a documented contract — never which artifact the fix touches: API changes, schema alterations, and migrations are routine execution when the mandate determines their shape, and derived artifacts (regenerated schemas, generated clients) are consequences, not decisions. The gate fails only when the fix forces a **pick** among behaviors the spec would accept either of — two defensible semantics, a default observers will see differently, a reinterpretation of persisted data nothing settles. "Observable" reads wide: the application's users and callers, plus shared operational surfaces — CI configuration, dev-stack resourcing, deploy config — that sessions and people beyond this issue's run rely on. The tell is never "am I editing a schema?"; it is "did I just pick?"

All three pass → delivering the fix is **in-mandate, auto mode included**: the exclusion was a hypothesis and this session falsified it. Two overlays before applying: a crossing whose diff lands on a **shared operational surface** (the `solo` class — the root `package.json`, the shared check suite, CI/dev-stack/deploy config) is not fleet-concurrent even when pinned — while a fleet is running, route it out below instead of applying it; and the crossed files were invisible to certification-time collision edges (they appear in no criteria), so an unattended session re-runs the sibling-issue search on them (`/start` Step 6 item 2's form) before applying. Then record the crossing and its evidence per the valve above.

Any gate fails — or the exclusion is `(decided:)` — do not cross, and do not go quiet. When the stated outcome still ships **and verifies** within bounds: ship it, and — when a genuine pick or human act is pending — file the excluded fix as its own issue carrying the evidence, labeled by `/auto`'s shape test, through `/quality-review`'s filing recipe — never a raw create. A decision-shaped filing takes that recipe's needs-decision exception: `specified` withheld, `needs decision` attached after create. A human-performed gate files `human` instead — attached after create the same way — and keeps `specified` when its body meets the bar: a `human` issue is certifiable, since the label records the executor, not spec quality. When nothing is pending — the outcome satisfied, the excluded path a mere stronger refinement — the either/or section's rule governs instead: a recorded reason, no automatic filing. When the outcome cannot ship or cannot verify without the crossing, stop: interactively, surface it — reopening a boundary is the user's move; in auto mode, return the issue per `/start` Step 8.5's ABANDONED mechanics with a decision-shaped `BLOCKED-ON-REVIEW` line naming the pick, which `/auto`'s human-gated-stops rule parks under `needs decision`. Either way, **route the decision, not the doubt**: present the evidence as settled ("root cause is X, measured: …") and frame only the choice as open ("raise the VM to N?") — this is never an is-the-agent-right escalation, and the human must be able to answer without re-running the diagnosis. The falsified exclusion's text is corrected at the next `/spec` regroom, flagged in the completion comment — an in-flight run never rewrites the description.

**For this route, material difference is measured in behavior, never geography or size** — deliberately wider than the either/or section's within-the-issue's-files gate, which still governs stronger-arm delivery there: a root cause has no obligation to live near its symptom, so a fix landing in a different module than the spec imagined, touching more files, or making a bigger diff than expected is the normal shape of a falsified hypothesis — proceed. Two bounds survive: an unpinned observable pick makes scope material (gate 3), and a crossing that blows the one-focused-session size budget (this standard's sizing item) is itself a stop — route it out rather than absorbing an epic mid-session.

BF-1507 is the worked example. Its exclusion "capping concurrent stacks or sizing the Docker VM — a machine-resources decision" contained the root cause its Problem described (measured in-session: six stacks' 9 GiB of DB *reservations* against a 7.65 GiB Docker VM; the mysql2-segfault case stayed a pressure-aggravation hypothesis, recorded as such); its "worth its own issue if it recurs" condition had already fired — one OOM-killed container four days before the session, two more during it; and the excluded cause gated the issue's own verifiability — a full-suite run on the starved VM reproduces the infra failure the issue is about. Honored silently, the exclusion yields diagnostics shipped unverified onto a machine still configured to fail, and nothing filed. The gates adjudicate the exclusion's two limbs separately: **sizing the VM** fails gate 1 (machine state) — never crossed unattended; **capping concurrent stacks** is in-repo but fails gate 3 — a cap value nothing pins, on a shared operational surface (the shipped compromise was an advisory that warns without refusing, precisely because refusal was an unpinned pick). And because verification could not run within bounds, the honest unattended route is the stop branch: park with the measurements and hand the human a two-line decision. (Interactively the user reopened the boundary and the VM was resized in-session — the same evidence, the pick made hot.)

**Writing discipline, for every producer:** when the Problem's root cause is undiagnosed at filing time, exclude deliverables, not mechanisms — a mechanism-exclusion written before diagnosis pre-registers a wrong turn with the spec's own authority behind it. Write a mechanism-exclusion only to record containment a human actually chose, marked `(decided: <who/why>)` — the marker is reserved for a human's recorded call; an agent never writes it on its own judgment. `(assumed)` is a *reading* of unmarked text, never a marking to author: writing down a guess you know is a guess means leaving the exclusion out. `/spec` adds missing markings at regroom, when the interview settles who decided what. (Editor's note for this section itself: never restate gate 3 as a list of artifact types — a bare enumeration gets read as a checklist and misroutes mandated work to humans.)

## A success criterion that carries its own pattern IS the gate

A criterion embedding a literal regex, glob, SQL predicate, or field index — `SELECT COUNT(*) … REGEXP '<pattern>'` returning 0 — asserts that the pattern's matches are exactly the population the issue is about. That assertion inherits every blind spot of the pattern, and the blind spot here does not merely understate a survey: **the criterion is the acceptance gate, so whatever the pattern misses is certified as fixed.** A remediation issue closes green with the defect it was filed for still live — and the narrower the pattern looks, the more precise the criterion reads.

The quality bar forbids this twice already — "no verification-command blocks" and "testable and implementation-agnostic" — and both get read past, because a pattern over data feels like the *most* testable thing a criterion could say. State the criterion as the **property** the data must have ("no `versions` row still carries a live sign-up token") and leave the pattern to execution time, where it is derived against the code that produces the values. A criterion only one specific pattern can satisfy is one the filer answered on the implementer's behalf, from outside the code.

## Producers

- `/prd` — net-new epics + sub-issues (clarifying questions up front; single-issue runs certify on create, batches certify after collision edges are wired)
- `/spec` — grooms existing/Triage issues into shape (research → interview → signoff → certify)
- `/reflect` — a **trusted-pipeline carve-out**, not an instance of the quality bar above: auto-filed proposals certify by pipeline provenance (the adversarial verify + triage gate in `skills/reflect/SKILL.md`), not by the interview. Their body still carries problem (the observation), outcome (the ready-to-paste diff — for a config/doc edit, the diff *is* the desired outcome, not deferred implementation planning), and criteria (the checkboxes); the quality bar's template and no-implementation-planning items govern the `/prd` and `/spec` paths.
- `/quality-review` — files severity-carrying deferred items only (Critical/High/Medium), whose bodies it composes in the certifiable problem/outcome/criteria shape, and certifies only those that additionally meet this standard's quality bar (mechanism verified in code, bounded blast radius, testable criteria); an item below that bar files **uncertified** and waits for `/spec`. Severity is the filing gate, not the certification gate. Its Nice-to-Have lane never files. A filed item whose remedy passes the `simple` risk test under the mechanical-lane bound additionally takes `simple` (§ The `simple` label)
